# Reasoning-aware calibration for GPTQ

This example compares GPTQ calibration on Qwen3-8B using three data conditions:

1. **Full**: MATH-500 prompts and dataset solutions; every retained token contributes to GPTQ.
2. **Dataset masked**: the same prompts and dataset solutions; prompt tokens are forwarded as context but masked from the GPTQ Hessian.
3. **On-policy masked**: responses generated by the BF16 base model on the same prompts; prompt tokens are forwarded as context but masked from the GPTQ Hessian.

All conditions use the same 500 prompts and exactly 112,808 active Hessian tokens. The FP8 and MXFP4A8 results
use the `FP8_DYNAMIC` and `MXFP4XFP8` compressor schemes, respectively. `MXFP4XFP8` means MXFP4 weights with
dynamic FP8 activations. The optional W4A16 ablation uses the `W4A16` scheme.

## What the scripts do

| File | Purpose |
|---|---|
| `generate_on_policy_traces.py` | Loads the pinned MATH-500 calibration set, records prompt and dataset-response token IDs, and generates BF16 on-policy responses with vLLM. |
| `calibrate_gptq.py` | Builds one of the three token-matched calibration conditions and writes a compressed GPTQ checkpoint plus calibration statistics. |
| `run_experiment.sh` | Generates traces if missing, then runs the requested scheme/condition pairs. Different quantization jobs can use separate GPUs. |
| `run_evaluations.sh` | Serves BF16 and selected checkpoints with vLLM, runs the held-out Inspect MATH evaluation, then scores each log with Math-Verify. |
| `run_eval.sh` | Runs the held-out evaluation against an already running vLLM server. |
| `score_math_verify.py` | Scores full completions against full reference solutions and writes correctness and answer-token usage for every sample. |
| `compare_output_tokens.py` | Compares per-sample generated output tokens against BF16, including an exact bottom-k average without percentile interpolation. |

## Environments

Use separate environments for generation, GPTQ, and evaluation if their PyTorch or Transformers requirements conflict.

- **Generation:** a vLLM environment with `vllm`, `transformers`, and `datasets`.
- **GPTQ:** an environment with this checkout's llm-compressor dependencies installed. The script puts this checkout's `src` directory on `PYTHONPATH`.
- **Evaluation serving:** a vLLM executable that can serve the selected quantization schemes. The reported MXFP4A8 runs used vLLM `0.34.0rc1.dev948+gd2da27eb2`, compressed-tensors `0.20.1`, and an H100 80 GB GPU; this vLLM build selected `HummingMxFp4LinearKernel`.
- **Evaluation client:** install `requirements-eval.txt` into an environment with the Inspect CLI available. The reported scores used Inspect AI `0.3.263`, Inspect Evals `0.20.0`, and Math-Verify `0.9.0`.

The vLLM and compressed-tensors versions matter for MXFP4A8 serving. Older vLLM/compressed-tensors combinations may not have an MXFP4-weight/FP8-activation kernel.

## Regenerate traces and quantize

The default output is outside the checkout under `${XDG_CACHE_HOME:-/tmp}/llm-compressor-rac-gptq-qwen3-8b`.
Set `MODEL_PATH` to a local checkpoint or Hugging Face model ID. Existing trace and checkpoint outputs are reused.

```bash
GEN_PYTHON=/path/to/vllm/bin/python \
QUANT_PYTHON=/path/to/llmcompressor/bin/python \
MODEL_PATH=Qwen/Qwen3-8B \
CUDA_VISIBLE_DEVICES=0,1,2,3 MAX_PARALLEL=4 \
OUT=/data/rac-gptq-qwen3-8b \
bash examples/gptq/reasoning_aware_calibration/run_experiment.sh
```

The default run generates 500 traces with temperature `0.6`, top-p `0.95`, top-k `20`, seed `42`, and an 8,192-token
response cap. It then calibrates all nine combinations of `FP8_DYNAMIC`, `MXFP4XFP8`, and `W4A16` with the three
conditions. Set `CONDITIONS`, for example `CONDITIONS="FP8_DYNAMIC/full MXFP4XFP8/onpolicy_masked"`, to select jobs.
`GEN_TP` controls trace-generation tensor parallelism. Calibration jobs use one GPU each; `CUDA_VISIBLE_DEVICES`
selects available GPU IDs and `MAX_PARALLEL` limits concurrent calibration processes.

The MATH-500 rows are pinned to dataset revision
`6e4ed1a2a79af7d8630a6b768ec859cb5af4d3be`. For each problem, the masked conditions use the smaller of its gold
answer length and generated answer length. The full condition keeps all prompt tokens and allocates the remaining
active-token budget proportionally over gold-answer prefixes. Masked prompts remain in the model input as context.

## Evaluate checkpoints

The checked-in ID files exclude the 500 MATH-500 calibration problems from the 5,000-sample Inspect Evals MATH task.
Evaluation uses the same 4,500 held-out sample IDs, Qwen3 thinking mode, temperature `0.6`, top-p `0.95`, top-k `20`,
seed `42`, and an 8,192-token response cap. To run all available checkpoints:

```bash
VLLM_BIN=/path/to/vllm/bin/vllm \
INSPECT=/path/to/inspect/bin/inspect \
INSPECT_PYTHON=/path/to/inspect/bin/python \
BASE_MODEL_PATH=Qwen/Qwen3-8B \
CUDA_VISIBLE_DEVICES=0 \
OUT=/data/rac-gptq-qwen3-8b \
bash examples/gptq/reasoning_aware_calibration/run_evaluations.sh
```

By default this includes BF16, all six FP8_DYNAMIC/MXFP4A8 checkpoints, and all three W4A16 checkpoints. W4A16
evaluation results are not included in the research report because that ablation was quantized but not evaluated in
the reported run. Use `CONDITIONS="bf16 MXFP4A8-onpolicy_masked"` to run selected models. Set `EVAL_LIMIT=50` for a
quick subset; its logs are stored under a separate `evaluations-limit50` directory. Set `FORCE=1` to rerun an
already-scored condition.

`run_evaluations.sh` starts one vLLM server at a time and writes its serving log beside each Inspect `.eval` file.
To connect manually to an existing server, set `MODEL`, `PORT`, and `LOG_DIR`, then run `run_eval.sh` directly. The
score sidecar records Math-Verify correctness, parse status, sample/scorer errors, and generated output-token counts.

To compare each condition's output tokens with the BF16 baseline, pass the sidecar paths produced above:

```bash
INSPECT_PYTHON=/path/to/inspect/bin/python
"$INSPECT_PYTHON" examples/gptq/reasoning_aware_calibration/compare_output_tokens.py \
  --baseline /data/rac-gptq-qwen3-8b/evaluations/bf16/results.math_verify.json \
  --condition FP8-full=/data/rac-gptq-qwen3-8b/evaluations/FP8_DYNAMIC-full/results.math_verify.json \
  --bottom-k 450
```

The bottom-k set is selected by sorting the per-question quantized/BF16 output-token ratios from lowest to highest.
The script reports the arithmetic mean of those exact per-question percentages and the pooled token ratio for the
same questions. Its P90 uses the nearest-rank order statistic, not linear interpolation.

## Reported findings

The experiment results and caveats are in [`docs/research/gptq-rac-qwen3-8b-hdcharles.md`](../../../docs/research/gptq-rac-qwen3-8b-hdcharles.md).
For reproducibility, that entry reports the Math-Verify scores from the saved generations. Native strict answer
extraction substantially undercounted valid reasoning answers, so its exact-match values are not used as the
accuracy metric. Agent workflows for reproducing this study are documented in
[`reasoning-aware-gptq`](../../../.agents/skills/reasoning-aware-gptq/SKILL.md).
